# 多账号攻防验收

2026-10-12用户明确授权：“后续测试，可以多账号进行测试，并且后续肯定要有互相之间的开战行为的”。这是本项目后续验收范围与完成条件。当前尚未执行双方真实开战。

保留现有R18主号的普通成长、原库与任务进度。后续使用至少两个自有测试账号，分别记录UID、登录来源、客户端产物SHA、后端实例/配置、主城与兵力及所属小队/联盟；后台浏览器多会话与微信不同账号/实体机分别记录，不将前者表述为后者。

| 场景 | 玩家实际行为与完成条件 | 必须保存的证据 |
|---|---|---|
| 两号正常准备 | 两号各自登录、正常城建/训练/资源循环，核对当前保护状态和可交战前提 | 两份身份与资产快照、规则来源、产物/实例归属；无管理员发奖或时间改写 |
| A进攻B | 正常选择玩家城、手动编成、确认出征；到达后真实结算并返程 | A的发送/在途/战报与B的防守事件/战报，同一次战斗标识、结果和双方实际战损 |
| B进攻A | 在服务端允许的保护与军队状态下反向正常发兵，不能只验证单向攻击 | B的发送/战报与A的防守读数；双方回城、可用兵力和伤兵/阵亡变化 |
| 资源结算 | 按实际保护量、仓容及抢夺规则核对攻方携带与到账、防方扣减；无收益时同样照实记录 | 开战前后双方资源、负载、回城时刻、服务端战斗/事件回执，避免单读客户端飘字 |
| 门禁与失败 | 新手/受害保护、圈层/距离、闭城、兵力不足等当前规则出现拒绝时保留首红 | 原始业务错误与双方当时状态；拒绝不是已开战，不为过验收改规则或伪造胜利 |
| 社交联动 | 原队列对应阶段继续核验同盟/小队权限与战争关系；涉及集结时核对发起、加入、退出与双方结算 | 各实际参与账号身份、权限与事件，不用夹具替代已要求的真实互相开战 |

先完成当前采集入口与原账号资源循环，再落实账号登记、交战前提和两个方向的真实流程。正常规则导致暂不可交战时先继续符合条件的成长路径，记录明确缺口；没有实际请求/服务端结算/双方读数就不标完成。无需为使用自有多账号或正常账号之间开战重复询问同类授权。账户费用、对外消息、真实用户攻击与前台电脑控制沿用既有边界。
