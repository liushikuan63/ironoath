# 核心设计提示词 · 目录

> **技术栈**：客户端 Cocos Creator 3.8 + TypeScript ｜ 服务端 **Java 17 + Spring Boot 3.x**
> 跨语言一致性策略见主文档 §1.5 与 B00。核心提示词中所有"服务端"均指 Java 实现。

> 与 `SLG提示词批次/` 的区别：
> - **批次提示词**（B01~B16）说「**做什么**」——功能清单、接口契约、验收标准
> - **核心提示词**（C00~C08）说「**为什么、以及 AI 会怎么错**」——设计公理、反直觉条款、自检清单

---

## 为什么需要这一层

批次提示词有个致命弱点：**AI 在写第 600 行代码时，早就忘了第 3 行的设计原则**。

更麻烦的是，AI 的训练语料里充斥着「游戏要平衡」「要保护新手玩家」这类**正确的废话**。当你让它实现战力保护，它的默认倾向是：

> "为了不让弱者被欺负，应该禁止强者攻击弱者，并给弱者一定的补偿。"

这个回答听起来完全合理，但它会**同时摧毁强者的付费动力和弱者的社交动力** —— 项目死掉。

这类错误无法靠"验收标准"兜住，因为代码跑得通、测试也过得去。必须在写代码之前，用一条明确的设计公理把它的直觉扭过来。

**所以核心提示词的写法是：先预判 AI 会怎么错，再写正确的做法。**

## 使用方式

### 场景一：开新批次前做设计评审（推荐）

```
1. 发 B00 共享上下文
2. 发对应的核心提示词（如做 B08 就发 C01）
3. 让 AI 回答里面的「设计评审三问」并输出自检清单
4. 评审通过后再发批次文件开始写代码
```

### 场景二：AI 做偏了，用它纠偏

```
1. 发核心提示词的「AI 的默认错误直觉」章节
2. 发 AI 刚才产出的代码
3. 问：你犯了其中哪几条？改。
```

### 场景三：每个核心文件末尾的「设计评审提示词」

可直接复制投喂，让 AI 对自己的设计做一次批判性自检。

## 三个 ★★★ 的地基

| 文件 | 做错的后果 |
|---|---|
| **C01 非对称平衡** | 生态崩坏：强者不付费、弱者不社交，两头空 |
| **C02 数值曲线** | 游戏不好玩，且无法调整（所有数值耦合在一起） |
| **C07 通胀控制** | **半年后必死**：资源溢出，付费失去意义，老服变鬼服 |

> C07 是这套文档里唯一一个「短期看不出问题、长期致命」的设计。它也是 SLG 最常见的死法 —— 不是上线即死，而是半年后缓慢死亡，等到发现时已经救不回来。

## 每个核心文件的固定结构

1. **一句话设计公理** —— 整个文件的灵魂
2. **AI 的默认错误直觉** —— 预判它会怎么错（**本文件的核心价值**）
3. **正确的设计** —— 规则 + 数学表达
4. **反直觉条款** —— 明确禁止什么，以及为什么
5. **自检清单** —— 设计评审逐项打勾
6. **设计评审提示词** —— 可直接复制投喂
