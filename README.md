## 怎么用

每个批次**单开一个对话**，按下面顺序把内容贴给 AI：

```
1. 先发 B00_共享上下文.md 的全文       ← 每次都要发，防止 AI 失忆
2. 再发 当前批次文件（如 B05_...md）的全文
3. AI 输出后立刻跑单测，通过了再进下一批次
```

**为什么每个批次都要带 B00**：AI 的上下文会随代码量增长而被稀释，到第 3 个文件就可能忘记"数值零硬编码""服务器权威"这些铁律。B00 相当于每次重新注入项目宪法。

## 文档体系总览（AI 装配规则）

这个仓库的文档分六类，**每类只有一个用途**。给 AI 派活时按任务类型装配，不要整目录投喂。

**开工三步（B16 之后的批次都适用）**：

1. **装配**：B00 + 批次文件 + 批次文件点名的 C 文档；批次有「〇、现状」段时，**先自己现跑复核一遍**
   （一条只干这件事的命令：`grep` / `node` / `ls`），不要相信文档里的状态描述。
2. **裁决前置**：批次文件 §五 的开放问题**先问再写**；没有答案就停在"验收清单"这一步（`收口清单.md` §三 的口径纪律）。
3. **收尾四条**：`bash scripts/test.sh`、`bash scripts/check.sh`、headless 构建、真启动 + `verify-b01.sh` —— **同一轮跑完**才算"全绿"。

**三条防腐纪律**（本仓库最贵的教训，逐字执行）：

- **文档里的计数与状态引用前必须现跑**（`grep -c '^bash scripts/' scripts/check.sh`、表行数、端点是否存在）。
  「文档说 A、代码是 B」时**先信现跑结果**，再把文档改对 —— 本仓库出现过"文档写着缺口、代码早已实现"的漂移。
- **「判定写了没接上」是头号缺陷形状**：实现完用「生产调用点计数」复核
  （`grep -rn "\.方法名(" server --include=*.java | grep -v test`），而不是"类里有这个方法"。
- **待裁决不发明**：找不到出处的数字与规则，写进批次文件 §五 或收口清单，不要替产品决定。

**B16 之后新批次的固定结构**：沿用下方「每条提示词的固定结构」七段，**另加一段「〇、现状（现跑）」** ——
这些批次是在活代码库上做增补，不写清"现在有什么、缺什么"，AI 会重造已有的轮子。

## 每条提示词的固定结构

本包所有批次文件统一采用这个结构，缺一不可：

1. **任务** —— 一句话说清这个批次交付什么
2. **依赖与前置** —— 需要哪些批次已完成，以及需要哪些配置表就位
3. **必做清单** —— 拆到可执行的功能点
4. **输入 / 输出契约** —— 精确的接口签名、数据结构、错误码
5. **验收标准** —— 可执行的、带具体数字的验证项
6. **禁止项** —— 明确告诉 AI 别做什么（这比"要做什么"更能防止跑偏）
7. **开工提示词** —— 可直接复制粘贴给 AI 的启动语

## 一个提醒

如果 AI 在某个批次反复做不对，优先怀疑**提示词的验收标准不够具体**，而不是模型能力问题。把"要优化性能"改成"拖动地图 60 秒内存增长 < 10MB"，AI 的表现会有质的差别。
